## 二、根本原因：APP_DOWNLOADING case 的逻辑差异（★最重要★）

### 用户 manage_jmp.c:

```c
case APP_DOWNLOADING:  // ota_status = 0x11
    log_a("App dowload failed");
    Jump2App();   // 跳转失败后直接 break，回到 while(1)
    break;
```

### 示例 Boot_Manager.c:

```c
case APP_DOWNLOADING:  // ota_status = 0x11
    log_a("App dowload failed");
    JumpToApp();   // 跳转失败后代码"掉落"继续向下执行！
    log_a("No Valid App");
    fil_size = Ymodem_Receive(au8_test);  // ← 无限等待串口新固件
    // 完整的重新下载和安装流程...
    break;
```

**结论**：示例的 APP_DOWNLOADING 在跳转失败后会重新等待下载新固件（降级恢复逻辑），这是故意设计的。用户代码直接 break 跳过了这个恢复流程。两者行为不同，但用户代码路径本身不会导致卡死。

## 三、APP_DOWNLOAD_COMPLETE (0x22) case 差异（★严重缺失★）

### 用户代码（严重不完整）：

```c
case APP_DOWNLOAD_COMPLETE:  // 0x22
    ee_ReadBytes((uint8_t *)&t_u32_appsize, 0x01, 4);
    // app_size = t_u32_appsize;  ← 被注释！
    break;
    // 什么安装逻辑都没有！固件永远不会被安装！
```

### 示例代码（完整实现）：

```c
case APP_DOWNLOAD_COMPLETE:
    ee_ReadBytes((uint8_t *)&t_u32_appsize, 0x01, 4);
    SetBlockParmeter(BLOCK_1, t_u32_appsize);  // 设置外部 flash 读取参数
    if(0 == ExA_To_ExB_AES(t_u32_appsize))    // AES 解密外部 flash A 区
    {
        ee_ReadBytes((uint8_t *)&t_u32_appsize, 0x05, 4);
        App_To_ExA(t_u32_appsize);  // 备份当前 APP 到外部 flash A 区
        ExB_To_App();               // 将解密后数据写入内部 flash
        JumpToApp();                // 跳转
        ExA_To_App();               // 回滚（跳转失败时）
        JumpToApp();
    }
    break;
```

## 四、BLOCK_SIZE 定义不同（★影响 W25Q64 所有地址计算★）

| | 用户工程 | 示例工程 |
|---|---|---|
| `BLOCK_SIZE` | `0x10000`（64KB！） | `0x1000`（4KB） |
| `Erase_Flash_Block` 返回 | `u8` | `void` |
| `SetBlockParmeter` 函数 | **不存在** | 存在 |

这导致 A/B 分区地址偏移相差 16 倍，所有 W25Q64 读写地址计算错误。

## 五、Flash_Write 调用 bug（ExA_To_App 中）

```c
// 用户代码 - Bug！（传了地址值，不是地址中的数据）
Flash_Write(FlashDes, RamSource);

// 示例代码 - 正确（解引用取实际数据）
Flash_Write(FlashDes, *(u32 *)RamSource);
```

## 六、跳转前未清理中断状态

用户和示例的 Jump2App/JumpToApp 都没有清理 NVIC 中断状态。APP 是 FreeRTOS 应用，启用了：
- USART1_IRQHandler
- DMA2_Stream2_IRQHandler
- TIM1_UP_TIM10_IRQHandler

Bootloader 跳转前若未清除 NVIC，APP 启动后 __enable_irq() 时这些中断立即触发，
而 HAL_UART_Init() 等初始化尚未完成，直接进入 Error_Handler → while(1)。

---

## 七、问题复现场景

**场景（最常见）：EEPROM 中 ota_status = 0x00，且有合法 APP（MSP=0x20006AB0，检查通过）**

1. 读 EEPROM → 0x00 (NO_APP_UPDATE)
2. Key_Scan 返回 0（未按键）
3. Jump2App 检查通过（0x20006AB0 & 0x2FFE0000 = 0x20000000）✅
4. 跳转到 APP（复位向量 0x080882F9）
5. APP 是 FreeRTOS 应用，__enable_irq() 后 USART1/DMA 中断触发
6. HAL 未初始化完成 → Error_Handler → while(1)
7. 表现为"复位无效"—每次复位都跳 APP，APP 立刻崩溃死循环

**注释掉 Ota_statemanage 为什么正常？**
→ 不调用 Jump2App，不跳转 APP，Bootloader 自己 while(1)，没有 FreeRTOS 中断冲突问题。

---

## 八、修复方案

### 修复 1（必须，解决复位失效）：Jump2App 前清理中断

```c
void Jump2App(void){
    if(((*(__IO uint32_t *)ApplicationAddress) & 0x2FFE0000) == 0x20000000)
    {
        __disable_irq();
        
        // 清除所有 NVIC 中断使能和挂起位
        for(int i = 0; i < 8; i++) {
            NVIC->ICER[i] = 0xFFFFFFFF;
            NVIC->ICPR[i] = 0xFFFFFFFF;
        }
        // 停止 SysTick
        SysTick->CTRL = 0;
        SCB->ICSR |= SCB_ICSR_PENDSTCLR_Msk;
        
        NVIC_SetVectorTable(FALSH_BASE_ADDR, 0x8000);
        RCC_DeInit();
        
        JumpAddress = *(__IO uint32_t *)(ApplicationAddress + 4);
        __set_MSP(*(__IO uint32_t *)ApplicationAddress);
        Jump2Application = (pFunc)JumpAddress;
        Jump2Application();
    }
}
```

### 修复 2：补全 APP_DOWNLOAD_COMPLETE 逻辑（参考示例完整实现）

### 修复 3：BLOCK_SIZE 改为 0x1000

### 修复 4：Flash_Write 调用改为 `Flash_Write(FlashDes, *(u32 *)RamSource)`

### 修复 5：在 APP 的 main() 中，确保在 HAL_Init()/MX_USART1_UART_Init() 之后才 __enable_irq()

## 九、快速诊断方法

在 Keil 调试模式：
1. 下载程序，不运行（Reset + Stop）
2. 在 `ee_ReadBytes(&ota_status, 0x00, 1)` 之后设断点
3. 运行到断点，查看 `ota_status` 的值
4. 如果是 0x11 或 0x22，用 `ee_Erase()` 清除 EEPROM 后重测

**如果实施修复 1（清中断）后依然失效，说明问题在 APP 侧，需要检查 APP 的 HAL_Init() 和中断初始化顺序。**
